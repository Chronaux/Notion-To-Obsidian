# Профили экспорта: спецификация v1 (реализована в 0.6.0, с ограничениями)

> **Статус:** основные настройки, оба профиля и JSON реализованы в 0.6.0. Профиль «База знаний» по умолчанию сохраняет прежнее поведение. Редактирование переопределений отдельных баз сейчас доступно в JSON (не через отдельную форму GUI). Предпросмотр доступен отдельной кнопкой, а не запускается автоматически при выборе ZIP. Исходный формат — только Notion **Markdown & CSV**.

## Цель и принципы

Сделать конвертер применимым к произвольным базам знаний, не теряя текущий результат для существующей базы. Разделить:

1. **Инварианты конвертации** — обработка UTF-8/Markdown, корректные внутренние ссылки и резервные переходы к странице, защита путей/дубликатов, контроль вложений, отсутствие перезаписи существующего Vault. Не переключаются пользователем.
2. **Правила представления** — иерархия, место баз, таблицы, оглавления, свойства, оформление и дополнительные файлы. Настраиваются профилем.
3. **Операционные параметры запуска** — исходный ZIP, новый каталог Vault, флажок отчёта и отмена. Не сохраняются в публичном профиле.

**Особенность миграции:** прежде чем менять значение по умолчанию для GUI, необходимо реализовать и проверить профиль «База знаний» в режиме совместимости с текущим v0.5.14. Поэтому в GUI и CLI оставлено прежнее поведение по умолчанию.

## Профили

- **Универсальный (рекомендуемый новым пользователям).** Сохраняет физическую иерархию Notion, не группирует страницы по тематическим заголовкам, не выносит БД в корень и не добавляет без необходимости служебные заметки/плагины. Делает необходимые преобразования для Obsidian.
- **База знаний (совместимость v0.5.14).** Повторяет принятые ранее решения для инструкции: восстановление разделов по корневому оглавлению, «Другие сервисы», верхняя папка «Базы данных», встроенные полные таблицы, локальные оглавления, CSS, вложенный плагин, стартовая заметка.
- **Пользовательский.** Копия одного из двух профилей с изменёнными настройками и, при необходимости, переопределениями для отдельных БД. Редактирование готового профиля автоматически создаёт несохранённую пользовательскую конфигурацию; не перезаписывает предустановку.

**Не часть профиля:** `write_report` — отдельный флажок GUI, выключен по умолчанию в обоих профилях, как в v0.5.14; поведение CLI и библиотечного API до отдельной миграции не меняется. `skip_missing_pages` — существующий отдельный флажок GUI, включён по умолчанию, остаётся доступным; при изменении алгоритма его можно расширить до стратегии `external / placeholder` без ложного «распознавания архивных страниц». Для адресов без достоверного Notion ID стратегия внешней ссылки требует осторожного разрешения; при невозможности оставить корректную ссылку сохраняется заглушка/предупреждение.

Обязательны для обоих профилей: корректировка относительных ссылок, сохранение внешних URL, идентификация UUID без вывода технических полей в Properties, переписывание вложений в локальные ссылки, копирование медиа, безопасные имена Windows, импорт записей CSV, сохранение исходных колонок и значений, отчётность в памяти, предотвращение перезаписи существующего Vault. `.notion-to-obsidian/import-state.json` сохраняется независимо от отчёта.

## Точность совместимости и обнаруженные жёсткие правила

Сейчас `src/lib.rs` содержит фиксированное `DATABASES_ROOT = "Базы данных"`, значение по умолчанию `"Другие сервисы"` для неразобранных разделов, анализ корневых `##`/aside и ширину 680 для столбцов `Ответ`, `Примечание`, `Текст`, `Text` (прочие 220; заголовок 320). Первая CSV-колонка считается заголовком записи. Все эти решения должны пройти через типизированные настройки, а не условие «если профиль == База знаний» внутри алгоритма.

Сейчас оглавление создаётся для страниц вне корня, если есть >=2 заголовков и нет уже готового оглавления. Для профиля совместимости нужно сохранить именно эти ограничения. Не следует генерировать синтетические `Оглавление.md` для папок: реальные файлы Notion с этим названием не удаляются. В версии 0.5.14 родительская статья с обычными подстраницами перемещается внутрь их каталога. БД и записи сейчас вынесены отдельно, но статья-родитель с внедрённой таблицей остаётся в дереве инструкций.

Нормализация имён тегов распознаёт `tag`, `tags`, `тег`, `тэг`, `теги`, `тэги`; пользовательский профиль сможет задать список колонок для тегов. В будущем нужен **перебор метаданных конкретной БД** перед выбором ключевой колонки, а не безусловное использование первой.

## Переопределения для отдельных баз данных

Базовые правила из профиля наследуются каждой БД. Можно переопределить:
- колонку названия записи по исходному **точному** имени (с проверкой на уникальность);
- имена колонок тегов и правило переноса конкретных свойств в Properties;
- ширину важных столбцов (в том числе длинных текстовых полей);
- представления Markdown/Bases и автоматическое встраивание базы в родительскую статью.

Для адресации БД при импорте допустим стабильный Notion UUID, но он **не выводится** в свойства заметок и не становится частью пользовательских имён. При экспорте/публикации профиля предлагается режим обезличивания индивидуальных правил, поскольку названия БД и колонок могут содержать личную информацию.

## Зависимости опций и валидация

- `separate_root` требует непустого безопасного имени каталога. При `source` поле имени скрыто/заблокировано.
- `markdown_only` выключает представления Bases; `bases_only` выключает встраивание блока Markdown-таблицы, пока не реализован и не протестирован другой вид встраивания; `markdown_and_bases` оставляет оба.
- `table_plugin` для полного текста активен лишь при генерации поддерживаемого представления и вспомогательных данных; не включать сторонние плагины автоматически в Obsidian.
- `restore_if_missing` не вставляет оглавление повторно; сохраняет существующее реальное оглавление и ссылки.
- Всякая смена стратегии папок должна пересчитать пути внутренних ссылок, Bases, embedded-блоков и вложений **до** рендеринга.
- Не вводить опций, способных отключить проверки безопасности, экранирование, целостность ссылок или контроль перезаписи.
- Не обещать реконструкцию недоступных CSV-данных Notion: формул, rollup, фильтров и признака архивности страницы.

## Конфигурационный формат (предлагаемый)

Версионированный JSON (уже есть `serde_json`) с явным `schema_version = 1` и идентификатором предустановки. Ниже — **пример**, не поддерживаемый текущей версией:

```json
{
  "schema_version": 1,
  "profile": "custom",
  "base_profile": "universal",
  "structure": {
    "sections": "source",
    "unmatched": "source",
    "parent_page": "inside_children"
  },
  "databases": {
    "location": "source",
    "output": "markdown_and_bases",
    "embed_in_articles": false,
    "title_column": "first",
    "widths": "uniform",
    "overrides": {}
  },
  "content": {
    "toc": "preserve",
    "callouts": "convert_keep_emoji",
    "tags": "auto"
  },
  "extras": {
    "start_note": false,
    "table_css": false,
    "table_plugin": false
  }
}
```

При чтении проверять версию схемы, типы, конфликты настроек и нераспознанные значения. `folder_name` и `unmatched_folder` задаются только в соответствующих режимах. Отдельная команда «Сохранить профиль» — не сохранять автоматически пути ZIP, назначения, URL исходных данных, отчёты или содержимое заметок. Импорт/экспорт профиля — локальные JSON-файлы по выбору пользователя, без установки и сети.

## Win32 UX / проект отдельного диалога

**Основное окно** в v0.6.0 расширено на строку профиля: ZIP, итоговый каталог, селектор «Профиль: Универсальный / База знаний / Пользовательский», кнопка «Настроить…», существующие чекбоксы отсутствующих страниц и отчёта, «Конвертировать». Версию не возвращать в заголовок окна, не возвращать кнопку «Проверить ZIP» или нижний постоянный поясняющий текст.

**Диалог «Настройки экспорта»** (нативный Win32, без Electron/WebView); текущие возможности и дальнейшие задачи:
1. «Структура»: источник иерархии, неназначенные страницы, вложенные родители;
2. «Базы»: расположение, формат, встраивание, колонки и индивидуальные переопределения;
3. «Содержимое»: оглавления, callout, теги;
4. «Дополнительно»: стартовая заметка, CSS, плагин, сохранение/загрузка JSON;
5. «Предпросмотр»: отдельная кнопка главного окна, показывающая счётчики и первые 32 рассчитанных пути; отдельный древовидный список и автоматический запуск после выбора ZIP — дальнейшая задача.

Выбор ZIP может автоматически запускать **лёгкий анализ** для предпросмотра, а не отдельную кнопку ручной проверки; не следует выполнять дорогое копирование вложений на этапе предпросмотра. Показывать «Изменено относительно профиля», «Сбросить к профилю», описание каждого неоднозначного правила и причины недоступности переключателя. Сохранять клавиатурную доступность, тёмную нативную тему, прогресс и отмену.

## Совместимость, порядок реализации и проверки

1. Добавить типизированную `ConversionOptions`, валидатор и пресеты в Rust; отделить выбранные настройки от состояния запуска. **Пока не менять вывод по умолчанию**.
2. Ввести snapshot/regression-тесты «База знаний == v0.5.14» на синтетических ZIP для иерархии, таблиц, ссылок, заглушек, Properties, callout и оглавлений.
3. Провести все ветки построения `paths()`, `hierarchy()`, `restore_toc()`, `inline_databases()`, `render()` через options; добавить тест «Универсальный» и комбинационные тесты.
4. Добавить нативный диалог GUI и сохранение/импорт профилей; синхронизировать CLI (при этом старый вызов CLI без профиля должен сохранить поведение для обратной совместимости).
5. Реализовать анализ ZIP и предпросмотр, затем провести DPI/клавиатурные и Windows smoke-проверки.

**Критерии готовности:** оба профиля на одних и тех же синтетических входных данных создают ожидаемые деревья; «База знаний» воспроизводит существующий вывод; нет утечки исходных значений/путей в код, профили или репозиторий; результат всегда создаётся в новом Vault; `cargo test --locked`, Windows build и существующие UI/CLI-проверки проходят. Не добавлять новые GitHub Actions workflow без отдельного запроса.

## Реализация v0.6.0 и оставшиеся доработки

- Реализованы типизированные варианты `ConversionOptions` в `src/options.rs`, JSON со строгой проверкой схемы, настройки отдельных БД по UUID, режимы таблиц Markdown/Bases, расположение иерархии, восстановление оглавления, callout, теги, плагины и CSS.
- Нативный диалог в `src/settings.rs` предоставляет основные опции и импорт/экспорт JSON. Правила конкретных баз, `databases.widths`, колонки заголовка и пользовательские столбцы тегов пока редактируются в JSON. Название папки неназначенных страниц можно изменить в диалоге.
- На главном экране имеется явный предпросмотр без сохранения файлов. Запланированный автопредпросмотр при выборе ZIP, визуальный просмотр **всего** дерева и индивидуальные редакторы БД остаются задачами следующего этапа.
- Историческая матрица «Универсальный» / «База знаний» выше отражает фактические значения по умолчанию. Для существующих пользователей в GUI выбран профиль «База знаний», а не «Универсальный»; это сделано сознательно ради совместимости.
